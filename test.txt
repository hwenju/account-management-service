Spring Boot 4.1.1 Migration — Agent Execution Prompts

项目背景与统一约束

当前任务是完成第一个 Java 项目的 Spring Boot 4 升级审查、必要修复、OpenRewrite Recipe 优化和技术总结。

项目基本情况

- JDK：21，本次升级保持不变。
- Spring Boot：3.5.14 → 4.1.1。
- 主要技术栈：Spring Framework、Spring Batch（chunk + tasklet）、Spring Security、Spring Data JPA、PostgreSQL、Jackson、ShedLock、Spring Cloud。
- OpenRewrite 仓库与目标应用仓库分开管理。
- 当前已经通过 OpenRewrite Recipe 和 AI Agent 对项目进行过迁移，不能假设现有代码一定正确，也不能假设所有迁移都是 Recipe 完成的。
- 之前的迁移过程、Recipe 修改记录、官方资料和历史讨论可能有参考价值，但必须重新核对当前实际代码。

必须遵守的工作原则

1. 以当前代码、依赖解析结果、Git 历史、测试结果和官方文档为证据。 不要因为历史对话中曾经得出某个结论，就直接认为它正确。
2. 所有重要结论都必须区分：
   - 已确认：有直接代码、依赖、官方资料或测试证据。
   - 合理推断：有技术依据，但尚未通过实际验证。
   - 未确认：目前缺少必要信息。
3. 不要把编译成功、应用启动成功等同于迁移完成。
4. 不要为了追求代码整洁而进行无关重构。优先最小改动、低风险和可理解性。
5. 不要随意新增异常类、抽象层、工具类或配置。每项改动都必须说明实际解决的问题。
6. 不要修改与当前任务无关的业务代码。
7. 修改前先说明问题、证据、拟修改位置和预期效果；得到明确阶段授权后再修改。
8. 不要臆测项目实际使用的功能，也不要把框架支持的能力说成项目已经使用的能力。
9. 不要把尚未验证的技术风险描述成已发生的问题。
10. 任何测试都要说明测试目的、覆盖范围、实际结果和未覆盖的内容。
11. 对版本和 API 兼容性，优先参考对应版本的 Spring 官方文档、Spring Boot Release Notes、Spring Cloud 兼容性资料及 OpenRewrite 官方文档。注意区分不同版本的文档，不要拿最新版本文档解释旧版本行为。
12. 如果缺少执行测试所需的环境、数据库或外部服务，明确指出阻碍，不得虚构测试结果。

阶段一：Spring Boot 4 迁移审查与自动化差距分析

任务目标

对第一个项目从 Spring Boot 3.5.14 升级到 Spring Boot 4.1.1 的实际结果进行完整审查。

本阶段只分析，不修改任何应用代码、POM、配置或 Recipe。

你需要同时检查：

- 目标应用仓库。
- OpenRewrite 仓库。
- 当前工作区 Git 状态。
- 可以获得的迁移前后代码、历史记录和测试结果。

最终要回答三个核心问题：

1. 当前项目的 Spring Boot 4 迁移是否正确？还存在哪些真实问题和需要验证的风险？
2. 现有 OpenRewrite Recipe 实际完成了哪些迁移？有哪些遗漏、误匹配或不合理的规则？
3. 哪些迁移任务值得继续自动化，哪些必须保留人工处理？

1. 先建立项目和仓库现状

先检查两个仓库：

- 仓库路径、当前分支、HEAD commit。
- 工作区是否存在已修改、未暂存和未跟踪文件。
- 当前迁移涉及的文件和目录。
- 是否能找到迁移前的版本、迁移前后的 Git Diff、Recipe 执行记录。
- OpenRewrite Recipe 的入口、配置方式和执行顺序。
- 哪些文件是 OpenRewrite 仓库的，哪些属于目标应用。

如果无法确认迁移前状态，不要猜测。明确说明证据缺失，并指出可以通过哪些历史提交、分支或备份补充证据。

2. Maven 依赖与版本兼容性审查

检查以下内容：

- pom.xml 中的 parent、BOM、dependencyManagement。
- Spring Boot、Spring Cloud 及其他相关组件版本。
- Maven effective POM。
- 完整依赖树，包括 compile、runtime、test 等 scope。
- Maven profiles 对最终依赖的影响。
- 直接依赖与传递依赖。
- 是否存在重复声明、显式版本覆盖和旧版本残留。
- 是否存在 Spring Framework 6 与 7、Spring Batch 5 与 6、Spring Security 6 与 7 混用。
- 是否存在依赖虽然能解析，但与 Boot 4 的实际运行环境不兼容。
- 是否有不必要的依赖、隐式依赖或应该显式声明的 starter。

重点检查：

- Spring Boot 4.1.1 与项目使用的 Spring Cloud 版本是否兼容。不能仅凭版本号推断，必须查对应官方兼容性资料。
- Spring Batch 是否正确升级到与 Boot 4 管理版本兼容的版本。
- Spring Security、Spring Data、Hibernate、PostgreSQL 驱动等是否由正确的 BOM 管理。
- ShedLock 的版本及其 Spring、JDBC 集成兼容性。
- 测试依赖是否仍然使用旧版 API 或不兼容的测试库。

注意：此前项目曾明确不考虑 Spring Batch 5.2.7 作为解决方案，不要重新把它作为推荐升级路径。

请输出关键依赖的版本来源、依赖路径和判断依据。不能只列出 dependency tree 中出现的版本，还要说明实际由哪个 BOM 或显式声明控制。

3. Spring Boot 4 Starter 结构审查

检查项目实际使用的 Spring 能力与 Boot 4 Starter 结构：

- Web MVC
- Validation
- Spring Batch JDBC
- Spring Security
- Spring Data JPA
- JDBC / PostgreSQL
- AOP
- Actuator
- Boot Test
- Security Test

确认：

- 哪些 Starter 已经正确使用。
- 哪些是通过传递依赖间接引入。
- 哪些需要根据项目实际职责显式声明。
- 是否仍然保留旧版 Starter 或不合适的依赖。
- 是否存在只因为传递依赖能够编译，就误以为依赖声明完整的情况。

不要机械地要求项目声明所有 Starter。每项建议都必须结合实际代码和运行职责说明原因。

4. Jackson 2 / Jackson 3 专项审查

这是本次升级的重点之一。

检查：

1. 所有 Jackson 2 相关依赖，包括直接依赖、传递依赖和测试依赖。
2. 所有 Jackson 3 相关依赖及版本。
3. 源码中 "com.fasterxml.jackson" 和 "tools.jackson" 的 import。
4. "ObjectMapper"、"JsonMapper"、"JsonNode"、模块、序列化器、反序列化器及相关注解的使用。
5. 自定义 Mapper Bean、手动创建 Mapper、Spring 自动配置 Mapper 的情况。
6. Spring MVC 的 JSON HttpMessageConverter 实际使用哪个 Jackson 实现。
7. 第三方依赖是否仍然要求 Jackson 2。
8. Jackson 2 兼容桥接依赖是否存在，具体解决什么问题。

特别注意：

- Jackson 3 的核心包名和 Jackson 2 不同，但注解包并不能简单地全部迁移到新包名。
- 不能仅凭依赖树中存在 Jackson 2 就断言应用正在使用 Jackson 2。
- 不能仅凭源码使用 Jackson 3 API 就断言所有 JSON 处理链路都已经切换到 Jackson 3。
- 不要为了清理依赖直接排除 Jackson 2，必须先确认第三方库和实际运行链路。

重点检查项目中的 "@JsonAutoDetect"、构造器、工厂方法、私有字段访问、DTO 序列化和反序列化行为是否受到影响。

输出：

- Jackson 2 依赖及来源。
- Jackson 3 依赖及来源。
- 源码直接使用情况。
- Spring MVC 运行时处理链路的证据。
- 可能的兼容问题。
- 是否有必要保留 Jackson 2。
- 需要补充的测试。

5. Spring Batch 6 专项审查

结合项目实际使用的 chunk、tasklet、JPA、JDBC 和 PostgreSQL，检查：

- Batch 6 API 和配置方式变化。
- JobRepository 配置和 "@EnableJdbcJobRepository" 等相关配置。
- JDBC 元数据表结构和 Schema。
- Sequence 命名、创建和使用方式。
- 事务管理器和 JobRepository 的关系。
- Job、Step、JobLauncher 等创建与执行方式。
- 历史 JobInstance、JobExecution、StepExecution 数据兼容。
- 已执行失败的 Job 是否还能正确重启。
- Batch 相关表结构升级是否可能影响历史数据。
- 自定义 Tasklet、ItemReader、ItemProcessor、ItemWriter 是否存在 API 或行为变化。

特别区分：

- 新环境初始化可以正常运行。
- 已有 Batch 元数据可以兼容。
- 历史失败任务可以恢复或重启。

这三者不是同一个验证结论。

6. Spring Security 7 与 Framework 7 专项审查

结合实际代码检查：

- Security 配置、FilterChain、授权规则和认证机制。
- 已弃用或移除的 API。
- Spring Security 7 与 Framework 7 的版本匹配。
- Spring Framework 7 的 "HttpHeaders" API 变化。
- 项目中是否把 "HttpHeaders" 当作 "MultiValueMap" 使用。
- Retry、Validation、HTTP Client 等相关 API 是否有行为或兼容性变化。

不能只通过搜索 API 名称判断问题，要结合调用上下文、类型和具体行为。

7. ShedLock 专项审查

检查：

- ShedLock 版本和 Provider。
- 数据库表结构。
- LockAtMostFor、LockAtLeastFor 等配置。
- 多实例并发执行时的行为。
- 锁获取失败时的业务处理。
- 锁释放及异常情况下的行为。
- 数据库时间与应用时间的影响。
- 升级后是否存在 Provider、注解或配置变化。

区分源码检查能够确认的事实，以及必须通过多实例或数据库集成测试确认的行为。

8. 其他迁移风险

结合实际代码审查：

- Validation API 和约束行为。
- Spring MVC 与异常处理。
- HTTP Client、连接池、超时和重试。
- Actuator 和健康检查。
- Logging 配置。
- JPA/Hibernate 行为。
- 自动配置条件。
- 配置文件属性重命名、删除或默认值变化。
- 第三方依赖兼容性。

不要为了覆盖面而罗列与项目无关的所有 Boot 4 变化。

9. OpenRewrite Recipe 实际效果审查

这是第二个重点。

请先识别：

- 使用了哪些官方 Recipe。
- 使用了哪些自定义 Recipe。
- 每个 Recipe 的入口和执行顺序。
- 原始 Recipe 与当前 Recipe 的差异。
- 哪些 Recipe 是 AI Agent 修改的。
- 每个 Recipe 具体负责什么迁移任务。
- 哪些修改真正影响了目标项目。

对重要迁移任务建立完整证据链：

"迁移前代码/配置 → Recipe 处理结果 → 当前最终代码/配置"

不能仅凭 Recipe 名称推断其功能，也不能仅凭当前代码推断它一定由 Recipe 生成。

如果无法通过 Git Diff 或执行记录确定来源，标记为来源不明。

10. 生成 Automation Gap Analysis

创建文件：

"Spring Boot 4 Migration - Automation Gap Analysis.md"

对重要迁移任务建立表格，至少包括：

字段| 内容
Migration Task| 迁移任务
Original Form| 迁移前代码或配置
Current Form| 当前代码或配置
Recipe| 对应 Recipe
Actual Result| 实际处理结果
Automation Status| 自动化情况
Genericity| 通用性判断
Risk| 误匹配或遗漏风险
Recommendation| 后续建议

自动化情况分为：

A. Recipe 已处理，并有证据验证。

B. 可以通过 Recipe 自动化，但当前规则遗漏。

C. 满足明确匹配条件时才适合自动化。

D. 需要业务语义判断，应保留人工处理。

E. 证据不足，暂时无法判断。

特别检查：

- 是否硬编码了当前项目包名、类名、方法名。
- 是否依赖某个业务字段或业务命名。
- 匹配条件是否过于宽泛。
- AST、类型、方法签名、注解匹配是否准确。
- 是否存在重复规则、冲突规则和顺序依赖。
- 是否出现为了让当前项目通过而添加的特殊规则。
- 是否存在自动化结果正确但难以解释、难以维护的情况。

本阶段只分析，不修改 Recipe。

11. 风险分类与报告

创建文件：

"Spring Boot 4 Migration - Technical Audit.md"

每个问题都要包含：

- 问题描述。
- 代码位置、依赖路径或官方文档依据。
- 当前状态。
- 影响范围。
- 具体影响机制。
- 严重程度。
- 验证方式。
- 是否阻塞最终迁移确认。

严重程度：

- Critical：已确认的严重兼容或正确性问题。
- Important：有明确技术依据，需要针对性验证。
- Minor：局部影响或维护性问题。
- Observation：技术变化或注意事项，目前没有发现实际问题。

另外将行动分为：

1. 必须修复或验证后才能确认迁移完成。
2. 可以继续推进，但需要补充验证。
3. 暂无必要修改，仅记录。

不要把所有不确定性都称为风险。每个风险必须有具体的影响机制。

12. 阶段一完成标准

完成后必须给出：

1. 项目迁移现状总结。
2. 依赖兼容性结论。
3. Jackson 2/3 结论。
4. Batch 6、Security 7、ShedLock 等重点结论。
5. 已确认问题与未确认风险。
6. Recipe 实际迁移覆盖情况。
7. 自动化差距分析。
8. 下一阶段需要解决的问题及其优先级。

最后回答：

- 当前迁移是否可以认为基本完成？
- 是否存在阻止迁移确认的问题？
- 哪些问题必须在阶段二处理？
- 哪些 Recipe 问题值得在阶段三修改？
- 哪些结论目前缺少证据？

本阶段不要修改任何代码、配置或 Recipe。

阶段二：迁移验证与必要修复

任务目标

根据阶段一的 Technical Audit，验证迁移问题并完成必要的最小修复。

不要重新无差别审查整个项目，也不要把阶段一列出的所有观察项都变成修改任务。

1. 先确认问题清单

读取：

- "Spring Boot 4 Migration - Technical Audit.md"
- "Spring Boot 4 Migration - Automation Gap Analysis.md"

对每个待处理问题确认：

- 是否真实存在？
- 证据是否充分？
- 是否影响当前项目？
- 是否必须在本次迁移中解决？
- 是否有明确的修复方案？

如果阶段一的结论存在错误或证据不足，先修正报告，不要直接按报告修改。

2. 制定验证计划

按风险设计针对性验证。

优先考虑：

- Maven clean compile。
- 单元测试和集成测试。
- 应用启动及关键配置加载。
- Jackson 关键 DTO 序列化、反序列化。
- Spring Security 认证与授权。
- Spring Batch Job、Step、Tasklet、Chunk 执行。
- Batch 历史元数据和失败任务恢复。
- ShedLock 多实例锁行为。
- 数据库访问和事务行为。
- HTTP Client 超时、错误处理和重试。

不是所有项目都必须执行以上全部测试。根据实际代码、外部环境和风险清单确定范围。

对每个测试说明：

内容| 要求
验证目标| 想确认什么
风险依据| 为什么要测
测试方式| 使用什么测试
预期结果| 什么结果算通过
实际结果| 真实执行结果
限制| 哪些情况没有覆盖

3. 必要修复原则

只有确认问题存在且修复具有明确收益时才修改。

修改要求：

- 优先最小改动。
- 不修改无关代码。
- 不随意重构。
- 不增加没有必要的异常类和抽象层。
- 不为了消除静态扫描告警而引入更复杂的实现。
- 不通过随意排除依赖来解决依赖冲突。
- 不改变原有业务语义，除非该语义本身就是已确认的问题。

每项修改前说明：

1. 原问题。
2. 证据。
3. 修改方案。
4. 为什么这是最小且合理的修改。
5. 可能产生的副作用。
6. 如何验证。

4. 测试结果必须真实

不得把没有执行的测试写成通过。

如果因为数据库、测试环境、外部 API 或权限不足而无法执行，要明确记录。

特别注意：

- 编译成功不等于运行正确。
- 单元测试通过不等于集成行为正确。
- 新环境初始化成功不等于历史数据兼容。
- 应用启动成功不等于所有业务链路正常。

5. 输出文件

创建：

"Spring Boot 4 Migration - Validation Report.md"

内容包括：

- 原始问题清单。
- 已验证的问题。
- 已修复的问题。
- 每项修改的 Git Diff 和原因。
- 执行过的测试及结果。
- 未能验证的事项及原因。
- 遗留风险。
- 当前项目迁移完成度和限制。

最后执行 Git Diff 检查，确认没有无关修改。

不要在本阶段修改 OpenRewrite Recipe。

阶段三：OpenRewrite Recipe 审查与优化

任务目标

基于第一个项目的真实迁移经验，优化现有 OpenRewrite Recipe，使其更准确、更容易测试、更容易复用。

当前没有第二个项目参与验证。因此，本阶段的目标是：

1. 确保 Recipe 正确解决第一个项目的迁移任务。
2. 尽量消除对第一个项目特有代码结构的依赖。
3. 通过独立测试验证通用性。
4. 明确尚未经过第二个真实项目验证的边界。

不能宣称 Recipe 已经适用于所有 Spring Boot 项目。

1. 先检查现有 Recipe

读取：

- 当前 OpenRewrite 仓库全部相关 Recipe。
- 原始 Recipe。
- 修改后的 Recipe。
- 阶段一的 Automation Gap Analysis。
- 阶段二的 Validation Report。
- 第一个项目迁移前后的 Git Diff。

逐条分析：

- Recipe 的实际职责。
- 官方 Recipe 与自定义 Recipe 的边界。
- 修改原因。
- 实际迁移效果。
- 是否存在重复或冲突。
- 是否有项目专属逻辑。
- 是否有更简单的实现方式。

不要仅根据 Recipe 名称或注释判断其作用。

2. 重新审查自动化边界

将规则划分为：

A. 通用迁移规则。

例如明确的依赖坐标变更、包名迁移、确定性的 API 替换。

B. 依赖类型、方法签名、注解等结构匹配的规则。

需要通过 AST、类型解析和精确条件控制范围。

C. 项目级规则。

只在明确的项目约定或配置下执行。

D. 业务语义规则。

需要人工判断，不应强行自动化。

优先使用官方 Recipe；只有官方 Recipe 无法覆盖、或者需要明确的项目级行为时，才增加自定义规则。

不要为了架构上的漂亮而过度拆分 Recipe，也不要为了减少文件数量把不同职责混在一起。

3. 检查匹配条件和误修改风险

逐条检查：

- 是否硬编码包名、类名、方法名。
- 是否硬编码业务字段和业务类。
- 是否通过字符串搜索替代类型匹配。
- 是否准确匹配方法签名和返回类型。
- 是否考虑静态导入、重载方法、继承和泛型等情况。
- 是否会误改同名但不同语义的方法。
- 是否会修改不属于目标迁移范围的代码。
- 是否可能重复添加依赖或配置。
- 是否存在 Recipe 顺序依赖。
- 是否重复修改同一 AST 节点。

每个自定义 Recipe 都应说明：

- 适用条件。
- 不适用条件。
- 匹配依据。
- 修改逻辑。
- 已知限制。

4. 建立测试

使用 OpenRewrite 官方支持的 Recipe 测试方式和项目当前使用的版本。

每个重要自定义 Recipe 至少考虑：

1. 正常匹配并完成迁移。
2. 不符合条件时不修改。
3. 不同包名和类名下仍然正确匹配。
4. 同名但不同语义的代码不应修改。
5. 边界情况。
6. 不应该修改的代码保持原样。
7. 多条 Recipe 组合后的结果。
8. Recipe 执行顺序。
9. 重复执行的幂等性。
10. Maven 依赖修改结果。

测试样例必须尽可能独立于第一个项目的具体包名、类名和业务名称。

不要只把第一个项目的代码复制进测试用例，然后就宣称通用性已经得到证明。

5. Recipe 结构与实现要求

可以根据职责考虑：

- Spring Boot 4 通用迁移。
- Spring Framework 7 API 迁移。
- Spring Batch 6 迁移。
- Spring Security 7 迁移。
- Jackson 3 迁移。
- 项目专属迁移。

但这些只是职责分类，不代表必须创建六个独立 Recipe。

实际拆分要根据规则数量、依赖关系和维护成本决定。

要求：

- 优先保留已经验证有效的规则。
- 只修改有明确问题的规则。
- 不进行无关重构。
- 不增加不必要的抽象层。
- 不为了展示复杂度而设计复杂的 Recipe 体系。
- 每条规则要有测试。
- 规则的适用范围要清楚。

6. 执行修改的流程

先输出：

- 当前 Recipe 问题清单。
- 拟修改规则。
- 修改原因。
- 预计影响。
- 测试方案。

确认方案后再实施。

修改时每完成一组相关规则，就执行对应测试，不要一次性修改全部规则后才检查结果。

7. 重新验证第一个项目

Recipe 修改完成后，使用第一个项目作为真实案例进行验证。

在安全的临时分支、临时工作区或可恢复的基线上执行，不要覆盖当前已经确认的迁移成果。

比较：

- 修改前 Recipe 的结果。
- 修改后 Recipe 的结果。
- 当前人工确认的最终迁移结果。

重点检查：

- 是否修复原有遗漏。
- 是否引入误修改。
- 是否重复修改已有正确代码。
- 是否影响不相关业务代码。
- 是否能重复执行。
- 是否有必要的人工迁移仍然保留。

不能为了让 Recipe 输出和最终代码完全一致，而把所有人工修改都硬编码进 Recipe。

8. 输出文件

创建：

"Spring Boot 4 Migration - Recipe Optimization Report.md"

内容包括：

- 原有 Recipe 的问题。
- 每条规则的修改原因。
- 修改前后的实现差异。
- 新增或修改的测试。
- 测试执行结果。
- 第一个项目的真实验证结果。
- 自动化覆盖范围。
- 必须人工处理的任务。
- 已知限制。
- 尚未通过第二个真实项目验证的内容。
- 未来第二个项目迁移时的使用和检查建议。

最后提供清晰的 Git Diff 总结，说明修改了哪些文件，为什么修改。

阶段四：Spring Boot 4 技术总结与团队分享

任务目标

基于前面阶段已经形成的审查、验证和 Recipe 优化结果，编写一份有实际价值的 Spring Boot 4 技术分享文档。

这不是 Spring Boot 4 官方升级指南的翻译，也不是简单罗列版本变化。

分享的核心是：

Spring Boot 4 到底改变了什么？为什么改变？我们项目实际改了什么？这些变化对未来开发有什么影响？

1. 必须使用的资料

优先使用：

- Spring Boot 4.1.1 官方文档和 Release Notes。
- Spring Framework 7 官方文档。
- Spring Batch 6 官方文档。
- Spring Security 7 官方文档。
- Jackson 3 官方文档。
- Spring Cloud 对应版本的官方兼容性资料。
- 当前项目迁移前后的代码和 Git Diff。
- Technical Audit。
- Validation Report。
- Recipe Optimization Report。

历史对话可以帮助定位问题，但不能作为最终技术结论的唯一证据。

2. 文档结构

第一部分：升级背景与整体变化

解释：

- 为什么项目升级 Spring Boot 4。
- Spring Boot 4 和 Spring Framework 7 的关系。
- Boot 4 与 Spring Batch 6、Security 7、Jackson 3 的关系。
- 这次升级不只是修改一个版本号，而涉及哪些基础设施和 API 变化。

第二部分：Spring Boot 4 的重要变化

重点讲解与项目相关的变化：

- Starter 结构调整。
- Spring Framework 7 API 和行为变化。
- Spring Batch 6 的变化。
- Spring Security 7 的变化。
- Jackson 3 及 Jackson 2 兼容问题。
- Validation、HTTP Client、Actuator、Logging 等实际相关变化。

每个主题都回答：

1. 原来的设计是什么？
2. 新版本发生了什么变化？
3. 为什么要这样改变？
4. 对开发人员有什么影响？

第三部分：项目实际改造

结合真实代码讲解：

- 原来如何实现。
- 现在如何实现。
- 为什么必须改。
- 修改后有什么实际影响。
- 哪些改动是 Recipe 自动完成的。
- 哪些改动需要人工完成。

尽量提供具有代表性的代码前后对比。

不要只罗列修改文件和依赖版本。

第四部分：项目获得了什么

严格区分：

A. 项目已经实际使用的能力。

B. 升级后可使用、但当前项目没有实际使用的能力。

C. 只是 API、依赖或内部实现发生变化，并不能直接称为业务收益的内容。

不要把版本升级本身包装成性能提升或功能增强。

第五部分：未来开发注意事项

面向日常 Java 开发人员，给出具体指导：

- 新代码应该使用哪些 API。
- Jackson 2/3 如何选择和处理兼容。
- Batch 任务如何配置和测试。
- Security 配置应注意什么。
- HTTP 请求、超时和重试如何设计。
- 如何避免升级后的依赖冲突。
- 哪些 API 不应该继续使用。

建议尽量配合项目实际代码示例。

第六部分：迁移经验

总结：

- OpenRewrite 适合自动化哪些确定性迁移。
- 哪些改动需要人工判断。
- AI Agent 在本次迁移中的实际价值和局限。
- 为什么应用启动成功不等于升级完成。
- 如何通过依赖树、Git Diff、测试和官方文档建立证据链。
- 如何降低未来升级风险。

第七部分：遗留问题和后续计划

明确列出：

- 已完成并验证的工作。
- 已完成但验证不充分的工作。
- 暂时无法验证的工作。
- 尚未解决的问题。
- Recipe 当前的通用性边界。

第二个项目尚未开始迁移，不要写成已经验证的成果。

3. 写作要求

- 以技术原理和实际案例为主。
- 适当解释底层设计，不要停留在 API 表面。
- 不要堆砌官方文档术语。
- 不要写成流水账。

- 让没有参与此次迁移的同事也能理解。
